# G-10: `.torrent` от провайдера — дизайн

Дата: 2026-11-02. Закрывает проектную часть G-10.

## Зачем

Провайдер пользователя режет UDP: DHT и udp-трекеры не работают (с 2026-11-02). С magnet список файлов приходит от пиров, поэтому раздача долго висит на «Получение метаданных» или не открывается совсем. В `.torrent` уже есть список файлов, размеры и полный список трекеров (часто HTTP). Если скачать его по HTTP, выбор файла появляется сразу, а трекеров для поиска пиров больше.

## Цели

- Rutor и YTS отдают ссылку на `.torrent` вместе с magnet:
  - rutor: ссылка `//d.rutor.info/download/<id>` из строки выдачи (есть в `rutor_search.html`), приводится к `https:`;
  - YTS: поле `url` у элемента `torrents` в ответе API.
  - Apibay ссылки не даёт, у него только magnet.
- Ссылка доходит до экрана раздачи вместе с magnet (маршрут навигации и `StreamManager.start`).
- `.torrent` качается только при выборе раздачи, не при поиске.
- Порядок при старте раздачи:
  1. есть сохранённый `.torrent` этой раздачи → берём его;
  2. иначе есть ссылка → качаем, проверяем, сохраняем;
  3. сбой на любом шаге или ссылки нет → magnet, как сейчас.
- Движок получает метаданные из `.torrent`. Трекеры из файла объединяются с запасными (`withFallbackTrackers`).
- Переход на magnet тихий: без надписей и без ошибки для пользователя.

## Не цели

- Ручной ввод URL и выбор локального `.torrent`-файла.
- Ссылки на `.torrent` у apibay и других провайдеров.
- Обход блокировки rutor на ТВ: там `.torrent` с rutor обычно не скачается, и сработает magnet. Это ожидаемо.
- Скачивание `.torrent` заранее при поиске.

## Антицели (провал даже при рабочем коде)

- Раздача с рабочим magnet перестала открываться из-за `.torrent` (любой сбой должен вести на magnet).
- Движку отдан чужой `.torrent`: info-hash файла не совпадает с хэшем раздачи из результата.
- HTTP-загрузка идёт на UI-потоке; выход с экрана не отменяет запрос и не закрывает сокет; `CancellationException` поглощается.
- Сохранённый `.torrent` переживает удаление своей раздачи или растёт без учёта лимита места.
- Меняются ключи позиций `bt:<hash>:<fileIndex>` или правила владения сессией `stream`.

## Поведение

### Загрузка и проверка

- Только `http`/`https`. Ограничение времени — 10 с на весь запрос; затем magnet.
- Предел размера — 5 МБ. Читать не больше предела, а не всё тело целиком; при превышении — magnet.
- Файл разбирается движком (bencode). Ошибка разбора — magnet.
- Info-hash из файла сравнивается с хэшем раздачи (тем, что даёт `engine.hashOf(magnet)`), без учёта регистра. Не совпало — magnet, файл не сохраняется.
- Ошибка HTTP (не 2xx), сеть, редирект на не-http схему — magnet.

### Хранение

- Файл лежит в каталоге раздачи `torrents/<hash>/`, имя — на выбор исполнителя, без пользовательских данных в имени.
- Запись атомарная: временный файл и переименование. Повреждённый сохранённый файл (ошибка разбора или чужой хэш) удаляется, дальше — шаг 2.
- Удаление раздачи `TorrentCacheStore` (вытеснение по лимиту, очистка) удаляет и файл. Размер файла учитывается в занятом месте или пренебрегается (до 5 МБ) — решение исполнителя, но запись не должна ломать проверки `TorrentCacheStore` (каталог раздачи, индекс, удаление «чужих» каталогов при запуске).

### Продолжение просмотра

- Отдельного списка «продолжить» нет: пользователь снова выбирает ту же раздачу в поиске, и позиция восстанавливается по `bt:<hash>:<fileIndex>`. Если файл ещё сохранён, сети для метаданных не нужно; если вытеснен — качается заново по ссылке из результата.

### Решения по проверке спеки (решение исполнителя спеки)

- Загрузка `.torrent` идёт в `StreamManager.start` **до** блока `NonCancellable`/`operations` и отменяется вместе с сессией; байты держатся в памяти. На диск файл пишется после `cache.initialize()` и `acquire(hash)`, поэтому очистка при запуске его не удалит.
- Сверка хэша: magnet провайдеров содержит v1 `btih`; файл принимается, если его v1 info-hash совпадает с ожидаемым. Чистые v2-файлы без v1 — magnet.
- Трекеры объединяются из трёх источников: файл, magnet результата, запасные. Без дублей.
- Разбор `.torrent` и получение хэша — метод `TorrentEngine` с реализацией по умолчанию (как `hashOf`), чтобы логику выбора пути тестировать на fake-движке без нативного кода.
- Редиректы между хостами разрешены (rutor отдаёт 302), только `http`/`https`, не больше 5.
- `TorrentResult.torrentUrl: String?` по умолчанию `null`; кэша результатов поиска нет, миграция не нужна.

### Тексты

- Новых пользовательских надписей нет.

## Ограничения и риски

- `TorrentCacheStore.initialize` удаляет каталоги, которых нет в индексе. Файл, сохранённый до `select`, может быть удалён при следующем запуске, если раздача так и не была выбрана. Это допустимо: в следующий раз файл скачается снова.
- Движок сейчас принимает строку magnet (`TorrentEngine.add(magnet, saveDir)`). Нужен явный вход: magnet или байты/путь `.torrent`. Не передавать путь к файлу под видом magnet.
- Повторное добавление того же хэша и проверки `uncertainAdds`/`removing` в `Libtorrent4jEngine.add` должны работать одинаково для обоих видов входа.

## Готово, когда

- unit-тесты: парсинг ссылки rutor и YTS; выбор пути (сохранённый → загрузка → magnet); fallback при таймауте, HTTP-ошибке, превышении размера, битом файле, чужом хэше; отмена загрузки закрывает запрос; атомарная запись и удаление битого сохранённого файла; ключи позиций не меняются.
- `testDebugUnitTest assembleDebug` через Docker.
- на ТВ (`armeabi-v7a`): раздача YTS открывается через `.torrent` (в логе видно, что использован файл); rutor на ТВ тихо уходит в magnet; продолжение раздачи берёт сохранённый файл; выбор файла и воспроизведение не изменились.
- STATUS, BACKLOG (G-10) и план синхронизированы.

## Оставлено исполнителю

- Имя файла, структура модели входа движка, место загрузки (отдельный класс или `StreamManager`).
- Логирование (без секретов; ссылки провайдеров секретов не содержат).
- Учёт размера файла в лимите.
